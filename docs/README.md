# 文件體系使用說明

> 本篇保留原版三層文件設計。整合版的規格位置、任務保存及驗證方式以 [INTEGRATION.md](INTEGRATION.md) 和 [WORKFLOW.md](WORKFLOW.md) 為準；下文 PLAN 用完即刪等規則只適用原版手動模式。

> **想直接開始用** → 看 [`WORKFLOW.md`](WORKFLOW.md)（操作步驟與指令範本）
> **想理解為什麼這樣設計** → 繼續往下讀

這套文件不是為了「文件齊全」而存在，是為了讓 AI 能可靠地寫出正確的東西。
每一份的存在理由只有一個：**這份資訊不寫下來，AI 或三個月後的你會做出錯誤決定。**

---

## 一、三層架構

六份文件依**生命週期**分成三層。判斷任何一份新文件該不該存在、放哪裡，就問它屬於哪一層。答不出來的，通常代表它不該存在。

```
常駐層「憲法」 = 不管做什麼功能都成立的事   -> 寫一次，持續修
功能層         = 這個功能專屬的事           -> 一功能一組，做完封存
執行層         = 這一輪對話專屬的事         -> 用完即刪
```

## 三、六份文件的完整屬性

| # | 文件 | 承載的 W | 誰寫 | **誰讀** | 生命週期 |
|---|---|---|---|---|---|
| ① | `docs/prd/NNNN-*.md` | why(產品) · who(使用者) | 人 | **人** | 每功能，做完封存 |
| ② | `docs/spec/NNNN-*.md` | what · who(actor) · when(時序) | 人（AI 協助） | **AI** | 每功能，實作期常駐 |
| ③ | `PLAN.md` | when(順序) | AI（人審） | **AI** | 用完即刪 |
| — | `CLAUDE.md` | how(執行) · who(AI) | 人 | **AI，每次** | 常駐，持續長大 |
| — | `docs/ARCHITECTURE.md` | where | 人 + AI 回寫 | **AI** | 常駐，改動慢 |
| ⑥ | `docs/adr/NNNN-*.md` | why(技術) · how(架構) | AI 草擬 + 人審 | **未來的人與 AI** | 永久，只追加不修改 |
| — | `CHANGELOG.md` | when(歷史) | 自動生成 | **人 / 外部** | 永久追加 |

> 「誰讀」是這張表最該注意的欄位：**PRD 是唯一給人讀的上游文件**，其餘全是餵 AI 的。
> 所以只有 PRD 可以敘事、可以長；其餘一律要短、要精確、要可驗證。

## 四、四條回饋線（這套流程活著的原因）

單看流程圖看不到這些，但它們才是讓文件不腐爛的機制。

### ① 成果回頭對 PRD　`⑤ ➜ ①`
測試過了只代表「做對了東西」，不代表「做了對的東西」。
拿 PRD 的成功標準核對，是唯一防止「高效率做錯事」的關卡。

### ② 實作反咬 SPEC　`④ ➜ ②`（最常發生，也最常被忽略）
AI 寫到一半撞到 SPEC 沒定義的情況時，**正確做法是停下來補 SPEC，不是讓 AI 自己決定**。
這條線沒建立起來，SPEC 三天就會跟程式碼脫節，變成一份騙人的文件。

### ③ 架構變更回寫　`④/⑥ ➜ ARCHITECTURE.md`
新增了模組、改了邊界，就回寫地圖。不然 AI 下次又把東西放錯地方。

### ④ CLAUDE.md 的成長機制　`④ ➜ CLAUDE.md`
**CLAUDE.md 不該一開始就寫完，它應該被 AI 犯的錯餵大。**
每次 AI 做錯一件你得糾正的事，問一句「這會不會重複發生？」——會，就補一行進去。
這樣它會長成一份專屬於這個專案的**錯誤防火牆**，而不是一份憑空想像的規範。

## 五、什麼時候該寫哪一份（決策樹）

```
有新想法
  │
  ├─ 要說服第二個人？或三個月後會想知道當初為什麼這樣定？
  │     是 ─▶ 寫 PRD
  │     否 ─▶ 壓縮成 SPEC 開頭三行（背景／完成標準／不做什麼）
  │
  ├─ 要開始實作了？
  │     ─▶ 寫 SPEC（沒有 Acceptance Criteria 就不准往下走）
  │
  ├─ SPEC 超過一次對話能做完？
  │     是 ─▶ 切 PLAN.md
  │     否 ─▶ 直接做
  │
  ├─ 實作中做了一個「以後有人會質疑」的技術選擇？
  │     ─▶ 補一份 ADR（含被否決的方案）
  │
  └─ AI 又犯了同一個錯？
        ─▶ 補一行進 CLAUDE.md
```

## 六、一個貫穿全部的原則

**能變成程式碼的文件，就不要寫成文件。**

```
可執行  >  可檢查  >  純文字
```

- **可執行**：型別定義、OpenAPI schema、測試、lint rules — 永遠不會過期，因為過期會編譯失敗
- **可檢查**：CI 檢查、pre-commit hook
- **純文字**：PRD、ADR、ARCHITECTURE — 只有這些擋不住，才用文字

純文字文件要留給**真正無法被編碼的東西**：why、trade-off、non-goals、被否決的方案。

理由是文件熵：每多一份純文字文件就多一個過期風險，而**過期文件對 AI 的傷害遠大於對人**。
人讀到不對勁會懷疑、會去問；AI 讀到會直接照做，而且理直氣壯。

## 七、常見錯誤

| 錯誤 | 後果 | 正解 |
|---|---|---|
| 把 PRD 直接丟給 AI 當實作依據 | 市場分析佔滿 context，模糊處被 AI 自行填滿 | PRD 給人看，用它生 SPEC，AI 只讀 SPEC |
| SPEC 寫了實作細節 | 綁死方案，AI 沒有發揮空間，也難維護 | SPEC 只寫 what 與驗收；how 交給 ADR |
| Acceptance Criteria 寫成散文 | AI 無法自我驗證，你變成唯一檢查點 | 寫成 Given/When/Then，且能對應到測試 |
| PRD 沒有 Non-goals | 範圍無聲膨脹，AI 過度發揮 | Non-goals 是 PRD 最重要的一段 |
| 為了補滿 5W1H 造 `WHO.md`／`WHEN.md` | 沒人更新，變成騙 AI 的假資訊 | 這三個 W 已分散在既有文件中，不需獨立檔案 |
| 一次把 CLAUDE.md 寫到兩千字 | 每輪吃掉大量 token，且多半是想像出來的規則 | 壓在一頁內，靠踩坑長大 |
| PLAN.md 做完留著 | 變成考古資料，誤導未來的 AI | 做完即刪 |

## 八、目錄對照

```
<專案根>/
├── CLAUDE.md                  常駐層 · 必須在根目錄
├── PLAN.md                    執行層 · 建議加入 .gitignore
├── CHANGELOG.md
└── docs/
    ├── README.md              ← 本文件（為什麼這樣設計）
    ├── WORKFLOW.md            ← 操作手冊（怎麼做）
    ├── ARCHITECTURE.md        常駐層
    ├── examples/              ← 填好的完整範例，僅供對照，勿直接複製
    │   ├── CLAUDE.sample.md
    │   └── ARCHITECTURE.sample.md
    ├── prd/
    │   ├── _template.md
    │   └── 0001-order-lookup.md      ← 範例
    ├── spec/
    │   ├── _template.md
    │   └── 0001-order-lookup.md      ← 範例
    └── adr/
        ├── _template.md
        └── 0001-shipment-status-cache.md   ← 範例
```

> **注意**：樣板庫裡 `CLAUDE.md` 與 `PLAN.md` 帶有 `.example` 副檔名，
> 複製進真實專案後要改回原本的檔名。原因見樣板根目錄的 `README.md`。

三份 `0001-*` 範例刻意使用**同一個功能**（訂單查詢），可以看出同一份資訊如何在 PRD → SPEC → ADR 之間流動、以及 PRD 的 why 與 ADR 的 why 是不同層級的 why。
