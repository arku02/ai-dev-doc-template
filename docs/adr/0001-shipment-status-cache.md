# ADR 0001: 物流狀態採背景同步快取，查詢不即時呼叫物流商

| | |
|---|---|
| 狀態 | 已採納 |
| 日期 | 2026-09-10 |
| 決策者 | 李大華 |
| 相關 SPEC | `docs/spec/0001-order-lookup.md` |

## 脈絡

SPEC 0001 要求訂單明細頁顯示物流狀態，且 PRD 0001 訂下 **P95 < 500ms** 的效能目標。

現有物流商 API 的實測數據（2026-09 連續七天，n=4,200）：

- P50 640ms、**P95 1,240ms**、P99 3,100ms
- Rate limit：**每分鐘 60 次**，超過回 429
- 可用性：該月有兩次共 47 分鐘的完全中斷
- 不提供 webhook 或任何推送機制（已與對方技術窗口確認）

尖峰時段訂單明細頁約 40 rps。若每次請求都即時呼叫，rate limit 在 1 rps 就會被打爆，且 P95 光是外部呼叫就超過目標值的兩倍。

產品端已確認（PRD 開放問題，2026-09-18 回覆）：**物流狀態延遲 15 分鐘內可接受**，因為物流商本身的狀態更新頻率也在半小時等級，即時查詢並不會拿到更新的資料。

## 決策

我們以**背景排程每 15 分鐘批次同步**物流狀態到本地 `order_shipment_status` 表，訂單查詢一律只讀本地表，**永不在請求路徑上呼叫物流商 API**。

同步範圍限定為狀態是 `shipped` 且下單在 30 天內的訂單，以控制 API 用量。

## 後果

### 正面

- 查詢路徑完全不依賴外部服務，P95 由本地 DB 決定（實測 < 80ms），效能目標有大幅餘裕
- 物流商中斷時查詢功能不受影響，只是資料變舊
- API 用量從「與流量成正比」變成「與待出貨訂單數成正比」，可預測且遠低於 rate limit

### 負面 / 代價

- **資料最多落後 15 分鐘。** 這是使用者可感知的。SPEC 要求回應必須揭露 `shipmentStatusUpdatedAt`，讓前端顯示「最後更新：X 分鐘前」，把不確定性攤開給使用者，而不是假裝資料是即時的
- 多了一個背景排程要維運。排程掛掉時查詢不會報錯，只會安靜地回傳越來越舊的資料——這是**沉默失效**，必須靠監控補
- 多了一張表與一份同步邏輯，整體複雜度上升
- 若未來要求「即時」，這個架構要大改，不是調參數就能解決

### 需要一併處理的事

- 監控：同步任務最後成功時間若超過 45 分鐘，發告警
- SPEC 已定義 `stale: true` 旗標（同步超過 60 分鐘），前端需顯示提示
- 同步任務需具備冪等性與失敗重試，單筆失敗不得中斷整批

## 被否決的方案

### 方案 A：每次請求即時呼叫物流商 API
- 做法：訂單明細端點直接串接物流商查詢。
- 否決原因：P95 1,240ms 單是外部呼叫就已超過 500ms 目標的 2.5 倍；且 rate limit 每分鐘 60 次，在 40 rps 的尖峰下第一秒就會被限流。**不是比較差，是在現有條件下做不到。**

### 方案 B：即時呼叫 + 短 TTL 快取（例如 60 秒）
- 做法：快取 60 秒，未命中才呼叫。
- 否決原因：首次請求仍承受完整延遲，P95 依然不達標（快取命中率推估僅 35%，因為使用者查詢分散在大量不同訂單上，不是集中在少數熱門資料）。且物流商中斷時，未命中的請求會直接失敗。

### 方案 C：等物流商提供 webhook
- 做法：改為推送模式，資料可近即時。
- 否決原因：已確認對方無此規劃，且無承諾時程。**這是最好的方案，但它不存在。**

### 方案 D：前端自行呼叫物流商查詢頁
- 做法：只顯示物流單號，附一個連到物流商官網的連結。
- 否決原因：使用者要多點一次、跳出站外，且物流商頁面在行動裝置上體驗不佳。PRD 的成功標準是降低客服工單，跳轉會顯著降低完成率。此方案作為 fallback 保留（快取無資料時顯示連結）。

## 重新評估的時機

- 物流商開始提供 webhook 或推送機制　→　方案 C 變可行，應改為推送
- 產品要求物流狀態延遲小於 5 分鐘　→　15 分鐘排程不再足夠，需重新設計
- 待出貨訂單數成長到使單次批次同步超過 10 分鐘　→　同步策略需改為分片或增量
