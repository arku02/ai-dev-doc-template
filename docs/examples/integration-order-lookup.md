訂單查詢涉及消費者／客服權限、外部物流服務、個資與稽核，應採完整流程。

## 3. 模擬一次需求變更：延遲目標縮短

### 3.1 模擬前提

為了演練「已交付功能再修改」的路徑，僅在本節假設：上述問題都已另行確認，先前版本已真實實作、驗收與封存，且產品已有清楚的 15 分鐘新鮮度目標及故障例外。這些前提沒有在本庫發生，不構成對 Q1～Q7 的實際解答。

模擬新需求：「正常情況下，物流資訊的新鮮度目標從 15 分鐘縮短到 5 分鐘。」此處的 5 分鐘是演練輸入，並非已核准的產品承諾。

### 3.2 實際推演

| 步驟 | 應執行的處理 | 避免的誤判 |
|---|---|---|
| 1. 分流 | 外部服務能力、排程、成本與故障承諾受影響，走完整流程 | 不因只改一個數字而走短流程 |
| 2. 開新變更 | 新提案引用現行規格與原變更；舊變更保持封存 | 不回頭修改舊任務成為新進度 |
| 3. 釐清定義 | 5 分鐘是本地最後同步年齡，還是相對真實物流事件的落後？故障例外是否改變？ | 不把輪詢頻率等同外部資料即時性 |
| 4. 產品回寫 | 若既有 PRD 明載該承諾，就更新其版本並由提案引用；產品目的不變的段落不重寫 | 不讓 ADR 單方面決定產品可接受延遲 |
| 5. 規格差異 | 對既有需求提出修改，補正常、臨界時間、失敗／陳舊情境 | 不先把新目標同步成已完成基準 |
| 6. 方案評估 | 檢查外部服務更新頻率、API 額度、訂單數、批次時間與重試；必要時新增取代 ADR | 不直接把排程從 15 改 5 就宣告達標 |
| 7. 檢查失效 | 舊 15 分鐘目標的設計與測試不能證明新目標；重新檢查受影響的任務、監控與驗收 | 不以舊通過紀錄抵銷新需求 |
| 8. 完成驗收後收尾 | 有最新證據才同步規格、更新實際架構與封存；不能達成則保留提案或明確放棄 | 不把文件封存當成功實作 |

### 3.3 技術可達性的反例

若每張訂單各需一次外部 API 呼叫，令待同步訂單數為 N、同步週期為 P 分鐘，忽略重試時的平均呼叫量約為 N/P 次／分鐘。

採用範例中的 60 次／分鐘額度，5 分鐘輪詢的理論平均上限為 N ≤ 300；這仍未保留重試與其他流量餘裕，且可能有瞬間突發限流。如果外部 API 可批次查詢，則需改用其真實批次容量計算。範例沒有提供這些資料，因此不能下可行結論。

即使平均額度足夠，也無法保證相對真實事件只落後 5 分鐘；物流商本身更新延遲仍是限制。此案例驗證「先查需求定義與可達性，再選技術方案」的回流路徑。

演練結果：回流規則能定位必須修改及重驗的項目；新需求仍屬待釐清，沒有實際測試通過或產品承諾。

## 4. 短流程與升級檢查

### 小修改控制案例

模擬需求：已驗收頁面上的固定標籤由「最後更新」改為「物流資訊更新時間」，不改資料、時間計算、互動或權限。

- 明確範圍：只修改該標籤及相應顯示驗收。
- 短提案與短設計足夠，不另寫產品 PRD 或 ADR。
- 如果現行規格逐字規定標籤，更新該需求；若只規定顯示同步時間，記錄行為契約未變及文案驗收，勿製造無意義的規格差異。
- 在同一任務清單中連結文字斷言與頁面檢視，檢查無溢出且原有時間與 stale 提示仍保留。
- 本庫沒有頁面，所以上述檢查未執行；OpenSpec 對「無規格差異」變更的實際操作留待工具試跑。

### 途中升級案例

如果修改標籤時發現還要讓訪客查詢訂單，這已涉及身份、權限與原 PRD 排除事項。應停止受影響的實作並回到需求分析，升級完整流程；若是可獨立交付的新目的，另開變更。不得以文案修改的授權順便加入訪客功能。
