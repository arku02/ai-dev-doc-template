# 第二版升級與既有 OpenSpec 專案整合規劃

整理日期：2026-09-19

公開版補註（2026-09-26）：本頁保留當時的升級規劃，不是執行入口。arxiv-digest 的完整試驗資料已另行備份；第二版特定案例的試用結果見 [試用摘要](reports/ARXIV-TRIAL.md)，不代表通用升級工具已完成。

本文件整理兩個問題的回答：

1. 「升級成第二版的目錄與工具配置」要怎麼做？有什麼規劃？
2. 這是否表示，已經使用 OpenSpec 的專案也可以整合？

**文件狀態：規劃說明。** 第二版的通用導入功能已完成；下述第一版升級工具，以及任意既有 OpenSpec 專案的自動整合，尚未完成。本文件不代表已開始執行遷移。

## 一、如何升級成第二版的目錄與工具配置？

建議把升級做成「第一版 → 第二版」的可重複遷移功能，再用 arxiv-digest 驗證，讓成果能回到 ai-dev-doc-template。

第二版將工作流程工具與依賴集中到 `.integration/`，讓產品程式與流程工具各自管理。升級需要調整工具位置、操作入口及說明，同時保留原有規格、歷史與工作成果。

### 已知的試用專案狀態

截至本次規劃前的檢查，arxiv-digest 沒有未完成的 OpenSpec 變更，已有兩筆封存紀錄；專案仍有未提交的檔案修改，升級時必須完整保留。真正套用前需再次核對，不能把這次檢查結果當作永久狀態。

### 步驟 1：產生升級清單

比對第一版工具與第二版，列出將新增、修改及保留的檔案。

- 辨識哪些檔案來自模板，哪些是專案自己的內容。
- 遇到自行修改過的工具檔，標示差異，不直接覆蓋。
- 確認是否存在未完成變更，以及目前工作狀態。
- 形成可核對的升級清單，再進入套用階段。

### 步驟 2：在副本完成遷移

先在獨立副本調整目錄、工具配置與操作說明。

| 內容 | 規劃的處理方式 |
|---|---|
| 正式規格、封存變更、歷史驗證紀錄 | 原位保留，不改寫歷史 |
| Python 程式、測試、帳密設定 | 保留 |
| 工作流程執行器、工具套件 | 改用第二版的 `.integration/` 獨立目錄 |
| 舊操作指令 | 優先保留相容入口，轉呼叫新工具 |
| 操作說明與工作規則 | 更新為正確的新位置與使用方式 |
| 舊工具檔 | 確認來源及新入口通過驗證後，再處理退役 |

舊指令如何保留、哪些舊檔可以退役，需在升級清單中明確列出，不預設直接刪除整個舊目錄。

### 步驟 3：驗證升級與復原

以 arxiv-digest 為第一個驗證案例，規劃檢查：

- 既有 14 項離線功能測試仍通過。
- 正式規格仍通過驗證。
- 規格、封存歷史與既有產品內容完整保留。
- 在副本中完成一次新變更，確認新工具能執行審查、測試與封存。
- 升級失敗時可依備份復原；若檔案在升級後又被修改，應停止自動復原，避免覆蓋新工作。

### 步驟 4：套用原專案，回收成通用功能

副本驗證通過後，再核對原專案是否出現新修改，備份後依升級清單套用。

將升級工具、衝突檢查、驗證案例、復原方式與操作手冊納入 ai-dev-doc-template，讓下一個符合條件的專案可以沿用同一套方式。

### 第一輪支援範圍與完成標準

第一輪限定支援：**我們自己的第一版模板 → 第二版。**

因為第一版的結構與來源已知，可以明確判斷哪些要升級、哪些必須保留。其他專案自行建立的 OpenSpec 流程差異較大，仍需個別比對。

完成標準是：**升級後舊資料與歷史完整保留，新流程可用，遇到衝突會停止，而且能在不覆蓋新工作的前提下復原。**

## 二、已經使用 OpenSpec 的專案也可以整合嗎？

可以作為整合方向，但要區分兩種情況：

| 專案現況 | 接入方式 | 目前狀態 |
|---|---|---|
| 使用我們的第一版模板，例如 arxiv-digest | 結構已知，可開發可重複使用的升級工具 | 已提出規劃，工具尚未完成 |
| 自己安裝 OpenSpec，使用原生或自訂流程 | 先比對規格、模板、設定與進行中的變更，再決定如何接入 | 需個別評估，尚無通用自動整合 |

### 整合後會加入什麼？

保留原有 OpenSpec 規格與歷史，再接入本模板提供的方法和檢查：

- **BMAD 規劃方法**：釐清問題、範圍、產品目的與架構取捨。
- **Spec Kit 澄清與一致性檢查方法**：確認未決問題、文件一致性，以及需求、任務與測試的對應。
- **測試與封存檢查**：要求真實測試證據，檢查證據是否過期，並驗證封存後的正式規格。

這裡的整合以 OpenSpec 作為流程工具，BMAD 與 Spec Kit 提供改編的方法與模板；不表示已把三套原生指令自動串接起來。

### 為什麼不能直接覆蓋？

已使用 OpenSpec 的專案可能有自己的正式規格、未完成變更、自訂模板與流程設定。直接覆蓋可能破壞既有工作或使規格與工具不一致。

因此，第二版通用導入入口遇到既有 `openspec/`、`workflow.config.json` 或 `.integration/` 時會停止，不自動合併或覆蓋。需要先比對，再形成遷移方案。

### 建議的擴充順序

1. 先完成「我們自己的第一版 → 第二版」升級能力。
2. 用 arxiv-digest 副本驗證保留、升級、交付與復原。
3. 將驗證成果整理成模板的正式升級功能。
4. 再逐步評估原生或其他自訂 OpenSpec 專案的接入方式。

arxiv-digest 可以繼續使用目前的流程，不需要因第二版已完成就立即重做；安排升級時，再依上述規劃處理。
