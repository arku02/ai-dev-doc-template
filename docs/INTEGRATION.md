# 整合工作約定（0.2.0）

| 項目 | 內容 |
|---|---|
| 狀態 | 本地 0.2.0；通用導入與乾淨環境結果見第二版報告 |
| 日期 | 設計 2026-09-17；落地更新 2026-09-18 |
| 目標 | 將現有文件樣板發展成單一、可追溯的 AI 開發流程 |
| 整合方式 | OpenSpec 管理變更，改編 BMAD 的規劃方法與 Spec Kit 的澄清／一致性檢查方法 |
| 驗證範圍 | 固定 OpenSpec 1.13.1，通用導入／復原、新／舊 Node 專案及無第三方套件的 Python venv；不涵蓋生產服務 |

本文件定義目標專案的工作約定。OpenSpec 管文件結構與同步；本庫的 workflow 入口補上可機械檢查的驗證關卡。產品判斷、語意審查與授權仍需由人或協作的 AI 處理，並非每條約定都已自動化。

目前使用 [整合操作手冊](WORKFLOW.md)；[原版手冊](WORKFLOW.manual.md) 保留供比較。[訂單查詢演練](examples/integration-order-lookup.md) 是設計階段紀錄；實際工具結果見 [試跑報告](reports/INTEGRATION-TRIAL.md)。

## 1. 整合範圍

本版只以 OpenSpec 作為流程工具。BMAD 與 Spec Kit 提供方法參考，改編後的提示詞與檢查內容由本樣板維護；不預設三套原生指令互通，也不維護三份任務狀態。

要完成的事：

- 讓需求、設計、任務與驗證能互相追溯。
- 明確區分現況、提案、已採納決策與歷史紀錄。
- 同一變更只有一份可修改的任務清單。
- 小修改可走短流程；涉及權限、資料契約或重大不確定性時增加必要檢查。

第一版已新增 starter、隔離示範與檢查程式。原有電商 PRD／SPEC／ADR 仍為歷史範例；示範採限定的假政策，不把原始未決問題當成已確認的真實產品設定。

## 2. 文件責任與唯一來源

「唯一來源」依資訊類型區分，不是用一份文件壓過所有其他文件。引用要保留來源連結與編號；若內容矛盾，先記錄差異，不能以較新、較詳細或已核准等標籤自行選邊。

下列是目標專案位置；可複製來源在 starter，已試跑實例在 examples/order-lookup。PRD 僅在需要時新增。

| 文件／位置 | 唯一負責的資訊 | 誰草擬與確認 | 更新與生命週期 |
|---|---|---|---|
| 專案守則（沿用目標專案入口） | 開發指令、共通原則、禁區、文件入口 | 維護者確認；AI 可協助整理 | 常駐；規則變更時更新 |
| `docs/prd/` | 產品問題、受眾、成功指標、產品範圍 | AI 協助；產品負責人決定 | 依產品目的維護；保留版本歷史 |
| `openspec/specs/<領域>/spec.md` | 已驗收並納入基準的行為契約 | 由已驗收變更同步 | 常駐；不得將未完成提案提前寫成現況 |
| `openspec/changes/<變更>/proposal.md` | 本次變更動機、範圍、不做事項、上游引用 | AI 草擬；範圍由負責人確認 | 活動期間可修訂；完成後封存 |
| 同一變更下的 `specs/` | 相對基準要新增、修改、移除的行為與驗收情境 | AI 草擬；行為歧義由需求負責人決定 | 活動期間可修訂；驗收後同步並封存 |
| 同一變更下的 `design.md` | 本次擬採方案、模組影響、資料流與取捨 | AI 草擬；重大技術取捨由技術負責人確認 | 明標擬採／已驗證；完成後封存 |
| 同一變更下的 `tasks.md` | 唯一實作與驗證任務、依賴、完成狀態 | AI 拆解及更新；審查範圍變更 | 完成後隨變更封存，保留追溯 |
| 同一變更下的 `review.md`（自訂） | 待決問題、來源版本、需求覆蓋、檢查結果與驗證證據 | AI 整理；需要人決策的項目記錄決策者 | 不另設任務清單；引用 `tasks.md` 的任務編號 |
| `docs/ARCHITECTURE.md` | 已存在的模組、依賴邊界與契約來源位置 | AI 依程式證據更新；技術負責人審查 | 實際架構改變後更新；無程式證據則不填現況 |
| `docs/adr/` | 重要技術決策的當時脈絡、選項、代價 | AI 草擬；技術負責人決定 | 提案可修；採納後保留原決策，新 ADR 取代舊決策 |
| `CHANGELOG.md` | 可對外說明的已交付變更 | 從實際交付內容整理 | 不記尚未實作的假成果 |

補充規則：

- PRD 的業務指標不等於程式驗收；「客服工單下降 30%」需要上線後觀測，不能以 API 測試通過代替。
- 現行規格記錄已採納的契約；程式若偏離它，要追蹤缺陷，不能默默把規格改成錯誤現況。
- 技術設計可以提前寫，但必須區分「觀察到的事實」「待確認假設」「擬採方案」。
- ADR 不得代替產品確認。例如可接受的延遲是產品承諾；背景排程週期是技術選擇，兩者須分別記錄。
- Schema、型別與 API 結構優先引用既有可執行契約，文件只補充目的與行為，不手動複製可生成的結構。
- 同一人可兼任產品與技術負責人；既有授權可直接沿用，不要求每一步重複批准。遇到新的業務歧義或超出授權才需決策。

## 3. 方法分工與交接

| 階段 | 方法來源 | 讀取 | 產出／更新 | 往下走的條件 |
|---|---|---|---|---|
| 需求探索 | BMAD 的產品分析 | 使用者需求、現有 PRD、已有系統證據 | PRD 或提案內的背景／成功標準 | 目標與範圍明確；假設有標記 |
| 建立變更 | OpenSpec | 專案守則、PRD、現行規格 | 提案、變更規格 | 有可驗證情境，沒有未決的關鍵行為 |
| 技術規劃 | 改編 BMAD 的架構評估 | 變更規格、程式、契約、架構現況、相關 ADR | 技術設計；必要的 ADR 提案 | 有方案依據；風險、限制與驗證方法清楚 |
| 拆解與審查 | 改編 Spec Kit 的澄清與一致性檢查 | 本次需求、設計、相關共通原則 | 唯一任務清單與審查紀錄 | 需求可追到任務及驗證；重要矛盾已處理 |
| 實作 | OpenSpec 執行流程＋目標專案開發工具 | 上述文件、相關程式 | 程式與任務進度、問題回報 | 改動留在授權範圍；待決問題阻擋相關工作 |
| 驗證 | 需求覆蓋檢查＋實際測試 | 最新規格、程式、測試結果 | 審查紀錄內的證據與結論 | 驗收通過，沒有會影響結論的過期檢查 |
| 收尾 | OpenSpec 同步／封存 | 已驗收變更與最新基準 | 同步現行規格、封存；必要時回寫架構／ADR／變更紀錄 | 同步內容與已驗收範圍一致，無未處理合併衝突 |

Spec Kit 的原生指令預期讀取自己的資料結構。第一版將檢查方法寫入自訂模板，不假裝可以直接對 OpenSpec 目錄執行原生指令。BMAD 的規劃結果以引用和整理方式交接，不另建可獨立修改的 SPEC 或執行任務清單。

## 4. 狀態與完成條件

本節是概念上的工作階段，不是 OpenSpec 原生狀態欄位。第一版以 review.md 的 pending／ready 表示內容審查、tasks.md 表示實作進度、工具生成的 evidence／receipts 表示驗證與封存；不另存一份容易失真的總進度。

`草擬 → 待實作 → 實作中 → 待驗證 → 已驗收 → 已封存`

- 草擬 → 待實作：範圍、可驗證規格、必要設計與任務已備妥；重大待決事項已解決。
- 實作中 → 待驗證：本次範圍的程式與必要測試已完成，可提交檢查。
- 待驗證 → 已驗收：檢查使用最新輸入；驗收條件與專案必要檢查通過，證據可查。
- 已驗收 → 已封存：規格同步成功，必要現況文件已回寫，活動變更已移入歷史。
- 任一階段發現待決問題：保留當前階段，記錄阻擋範圍與決策者；不相關且已授權的工作仍可繼續。
- 上游改動後：退回最早受影響的階段，重新檢查；不得保留舊的通過結論作為最新證據。

`review.md` 至少記錄：

| 欄位 | 內容要求 |
|---|---|
| 變更識別與階段 | 對應哪個變更、目前處於哪一步 |
| 本次檢查的輸入 | 文件路徑與 Git commit／內容摘要雜湊；未版控時保存明確修訂識別與差異 |
| 待決事項 | 問題、來源、影響、誰決定、決策內容與證據；不記成第二份實作任務 |
| 覆蓋關係 | 需求／AC 或設計檢查編號 → 任務編號 → 測試案例或人工驗證方法 |
| 實際證據 | 指令或人工步驟、執行環境、時間、退出碼或觀察結果、結果位置 |
| 結論 | 通過／未通過／未執行，以及受影響範圍；不能用「檔案存在」代表通過 |

只有寫出測試檔名不算執行過測試。文件演練不能將任何應用功能標成已驗收，也不能把它同步進現行規格。

基礎建設、同步與監控任務可對應技術設計或 ADR 的可驗證要求，不必虛構使用者行為 AC。仍須為該要求建立檢查編號、驗證方法及結果；每項範圍內需求也都必須有對應工作，不能只確認「每個任務都有來源」。

OpenSpec 的產物依賴與配置不能取代測試結果檢查。本版已由 workflow.mjs 核對輸入雜湊、實際 Node 或 Python unittest 結果及 R／D 案例編號；封存後也嚴格驗證正式規格。只在使用該入口時有自動阻擋效果。原生 archive、人工改檔或任意改寫檢查程式均不受這個本地入口限制。

## 5. 發現問題回哪裡修改

| 觸發情況 | 先處理的來源 | 連帶檢查／失效範圍 | 決策責任 |
|---|---|---|---|
| 產品目的、成功指標變動 | PRD；無獨立 PRD 則為提案 | 提案、規格、設計、任務、驗收 | 產品負責人 |
| 可觀察行為、權限或邊界不明 | 變更規格，記錄待決事項 | 相關設計、任務、測試；重大歧義阻擋相關實作 | 需求負責人；必要時技術負責人參與 |
| PRD 與規格範圍矛盾 | 同時列出兩個來源，確認預期範圍 | 不能只改其中一份；結論回寫來源後重審 | 產品負責人 |
| 只更換內部實作方式 | 技術設計；必要時新增 ADR | 相關任務、測試與架構影響 | 技術負責人或既有授權內的執行者 |
| 程式不符合有效規格 | 修正程式與測試 | 相關驗證重新執行 | 執行者；不藉改規格掩蓋缺陷 |
| 任務拆錯、依賴或估計改變 | 唯一 `tasks.md` | 任務覆蓋與依賴檢查 | 執行者；若改變需求範圍則回到產品決策 |
| 兩個活動變更修改同一條需求 | 比對最新基準及兩份變更 | 同步前解決差異，受影響變更重做檢查 | 相關負責人 |
| 已封存功能要再變更 | 建立新變更，引用舊變更與現行規格 | 新一輪規格、設計與測試 | 依新變更責任分工 |

已封存紀錄保留當時事實與結果；錯誤補充以可追溯勘誤記錄處理，不無聲重寫歷史。隱私去識別化是明確例外：允許移除個人路徑與機密資訊，但須留下整理紀錄、標示公開副本與雜湊驗證限制，不得補造通過證據，詳見 [去識別化與公開](PRIVACY-REDACTION.md)。已採納 ADR 的實質改變用新 ADR 記錄，並明列取代關係。

## 6. 大小兩條路

### 小修改

全部符合才使用短流程：

- 單一、明確的變更目的，驗收方式已知。
- 影響範圍可確認，沒有未決的重大行為。
- 不改權限、敏感資料處理、公開契約、資料遷移、金流或跨模組的重要邊界。
- 不需要新的重要技術取捨。

流程：短提案 → 必要變更規格與短設計 → 任務與精簡審查 → 實作／測試 → 同步／封存。

省略的是獨立 PRD 與冗長論述，不省略行為驗收、唯一任務清單與實際測試。若實際 schema 要求設計產物，保留簡短 `design.md`；不得因稱為「短流程」就繞過工具依賴。無行為變更時須明說理由，工具如何表示將在試跑確認。

### 完整流程

新產品、跨元件行為契約、資料完整性、重大未知、上述高影響變更，或短流程途中發現這些因素，採用完整流程。修改多個檔案本身不是升級條件，詳見 [第二版判準](RELEASE-0.2.md)。

流程：需求探索／必要 PRD → 提案 → 變更規格 → 技術設計／必要 ADR → 拆任務與一致性檢查 → 實作／測試 → 同步／封存。

升級流程時沿用同一變更及任務編號，補上缺少內容，不重開第二份進度清單。工作是否小，依影響與不確定性判斷，不依程式碼行數。

整合工具的讀寫限於指定專案與本次變更。試跑使用獨立目錄與假資料，沒有資料遷移、部署或外部通知；目錄隔離不是作業系統安全沙盒，仍沿用目標環境權限，不以模板指令擴大權限。

## 8. 驗證結果與下一階段

文件演練已定位原始矛盾；工具試跑另外驗證實際流程。兩者分開記錄，不能以工具成功聲稱原始電商問題已獲解答。

已建立的落地內容：

1. starter 內的五份模板、integrated schema、固定工具版本與 lockfile。
2. 新目錄初始化與可重播的完整／短流程示範，保存 CLI 輸出和驗證回條。
3. 整合測試覆蓋未決問題、失敗測試、空／跳過測試、證據過期、同需求衝突及重新審查。
4. 更新後的操作手冊與遷移說明；最終通過數以 [試跑報告](reports/INTEGRATION-TRIAL.md) 和實際測試輸出為準。

目前暫不支援純文件零 delta、RENAMED、獨立 store 或 Node 原生／Python unittest 以外的測試框架。Python 適配的歷史結果見 [實際專案試用摘要](reports/ARXIV-TRIAL.md)，原始試驗證據另行備份；公開可執行案例見 [Python 執行器測試](../tests/python-runner.test.mjs)。未來增加能力須補相應測試，不以模板能表達就宣稱工具已支援。

不要求為了格式齊全先補滿所有文件。例外或「不適用」須說明理由，不能省略會影響驗收的內容。
